# 计量分析主控（orchestrator）

本 skill 管理一个迭代式、人机协同的 agent 计量分析循环。它协调各个子 skill，
并在进入下一步之前检查每一步的经济合理性。

## 设计原则

1. **一切随时可改。** 任何阶段的任何决策都可以随时修改。框架从不把用户锁死在一条路径上。
   修改会自动向后传导，研究日志记录每一个版本。
2. **具体知识优先于模型自身知识。** 每个决策都先用具体来源，再用一般来源：依次是用户、
   模型字典、知识库（本地背景：经济体概况、数据来源、建模惯例）。只有出现空白时才退回到
   模型自身知识（parametric knowledge）。完整的优先级链在 `specification` skill 里统一定义；
   每个决策的来源都要公开说明。
3. **主动建议，人工确认。** 在每个选择点（模型类别、变量、滞后、先验、识别、样本区间、
   合理性补救、模式判断、数据替代），都提出具体建议，并给出依据（依次来自字典、知识库、
   模型自身知识 / 经济理论）。用户确认、修改，或要求其他方案。绝不默默继续；绝不在没给方案
   的情况下问"你想怎么做？"。agent 是对话伙伴，不是让人填的表格。
4. **经济合理性优先。** 每个中间结果都先对照经济理论检验，再接受。指出异常（价格之谜、
   爆炸根、不合理的量级）并提出补救办法。
5. **迭代改进。** 结果未通过合理性检查时，修改并重新估计；但自动修改只限于第 5 阶段规定的
   类别（实现 / 数据错误的修正，以及事先规定的统计规则）。经济上实质性的改动必须作为待确认的
   提案，并作为带标签的稳健性分析，与保留的基准结果并列运行。
6. **与技术栈无关，优先用现成包。** 按用户偏好的语言生成代码（Python、R、Julia、MATLAB）。
   始终使用最合适的现成库或包；不要从头重写标准算法。只有某个方法确实没有可靠的包时，
   才写自定义代码。
7. **完整记录。** 每个决策、每次迭代及其理由都通过 research-log 子 skill 记录，保证可复现。
8. **推荐默认值集中在一个文件。** 可调设置（先验超参数、抽样次数、图表风格、数据源偏好）
   的初始建议来自工作区根目录的 `config.yaml`。代码库不读这个文件：一次运行实际使用的值要写进
   该运行自己的 `config.yaml`（并作为显式参数传入），因为真正决定执行的是那个文件和那些参数。
   修改根目录的文件只会改变今后的建议，不会改变已有脚本；经典复现保持其声明的设置，除非偏离
   得到批准并记录在案。其中标注 `[lib constant]` 的字段只供参考。覆盖顺序：config.yaml <
   知识库 < 运行时指令（用户永远优先）。
   （唯一的有意例外：API key 的变量名、接口地址、速率限制放在
   `skills/data-retrieval/connections/connections.yaml`，因为它们属于凭据和连接配置，
   不属于行为设置。）

## 三种入口模式

一次会话可以从三种模式之一开始。主控的第一项工作（下面的第 0b 阶段）是判断请求属于哪种
模式，然后相应分流：

| 模式 | 适用情形 | 主控做什么 |
|---|---|---|
| **A：字典执行** | 用户点名的论文 / 方法在 [`model-dictionary/entries/`](../model-dictionary/entries/) 里有条目，且没有提供新内容 | 查条目，运行或生成 `replicate.py`，跳过设定设计 |
| **B：论文提交** | 用户提供了一篇论文（PDF / URL / 引用），字典里没有对应条目 | 解析论文 → 起草条目（`verified.status: draft`）→ 用户核对 → 转入模式 A |
| **C：研究设计** | 用户提出开放问题，没有点名方法 | 运行 `model-selection`；字典有匹配就升级为 A；否则依据模型自身知识设计 |

如果请求含义不清（例如既点名了论文、又提了开放问题），先问再继续。不要默默猜模式。
选错模式会让用户把时间浪费在错误的工作上。

三种模式最终汇入同一条执行流水线（第 2–7 阶段；无偏离的模式 A 跳过第 2 阶段），区别只在于
*进入*设定的路径。完整路径说明、模式转换示例和更深入的参考见 [`modes.md`](modes.md)。

### 来源层级

模式 A 的查找覆盖两个来源层级（草稿目录列出来只是为了完整，它不是来源）：

| 层级 | 目录 | 作用 | 是否 gitignore |
|---|---|---|---|
| **canonical（经典）** | [`scripts/replications/<id>/`](../../scripts/replications/) | 经典复现，已对照论文核验；公共示例库 | 脚手架纳入版本管理；`outputs/` 忽略 |
| **application（应用）** | [`scripts/applications/<id>/`](../../scripts/applications/) | 用户自己过去的分析（变体、改编、探索） | 脚手架纳入版本管理；`outputs/` 忽略 |
| **scratch（草稿）** | 工作区根目录的 `outputs/` | 本次运行的临时文件 | 始终忽略；可丢弃 |

模式 A 中经典层级排在应用层级前面，但两者都会列出。成功的模式 B、C 运行会被提升到其中一个
层级：默认提升为应用；只有经过严格核验（字典条目 `verified.status: checked_against_paper`
或更高）才提升为经典。

工作区根目录的 `outputs/` **不是**主控的来源，只是草稿区。它消失了也不会丢失任何脚本，因为
脚本放在对应的 `scripts/<tier>/<id>/` 目录里。生成的模型产出可以重新生成，但会话记录
（`session_research_log.json`、`research_log.md`、`run_state.json`、任何保存的计划）不能：
删除任何 `outputs/` 目录之前，先把它们复制出来。

### 模式转换

模式不是单向的。会话可以中途在模式之间转换：**C → A**（模型选择找到了干净的字典匹配）、
**B → C**（论文提取失败或方法太新）、**A → C**（用户偏离条目太远）、**C → B**（用户在设计
过程中拿出一篇论文）。每次转换都要明确告知用户并记录。示例见
[`modes.md`](modes.md#mode-transitions-extended)。

## 修改规程

研究不是线性的。用户会想回头改东西、看看会怎样。框架必须让这件事轻松，而不是让人受罪。

### 核心规则：任何阶段，任何时候

用户可以在工作流的任何时刻修改之前的任何决策：

- "还是把汇率加进模型吧" → 修改第 2 阶段，重跑 3–6。
- "试试 Minnesota 先验，lambda 收紧一点" → 只修改第 4 阶段，重跑 4–6。
- "能把同样的结果写成政策简报吗？" → 只修改第 6 阶段。
- "把 Cholesky 换成符号约束" → 修改第 2 阶段和 4–6。
- "样本改成从 2000 年开始" → 修改第 3 阶段，重跑 3–6。
- "我更新一下经济体概况" → 修改第 0a 阶段，可能影响之后的所有阶段。

### 修改怎样进行

1. **确定改了什么。** 解析用户的请求，判断影响哪些阶段。

2. **确定传导范围。** 修改只向后传导，从不向前：

   | 修改的阶段 | 必须重跑 |
   |---------------|-------------|
   | 0a（知识库） | 可能全部；检查哪些下游决策依赖了被修改的背景 |
   | 1（模型选择） | 2、3、4、5、6 |
   | 2（设定） | 3（若变量有变）、4、5、6 |
   | 3（数据） | 4、5、6 |
   | 4（估计） | 5、6 |
   | 5（合理性） | 6（若触发了重新估计） |
   | 6（呈现） | 仅 6（重新渲染） |

3. **保留没变的部分。** 用户只改了先验，就不要重新取数据。只改了受众格式，就不要重新估计。
   复用未变阶段的缓存结果。

4. **生成新版本。** 每次修改都在研究日志的 `version_history` 里增加一个版本（结构见
   [`research-log/SKILL.md`](../research-log/SKILL.md)）。旧版本从不删除，用户随时可以比较。

5. **展示差异。** 修改后重跑时，向用户展示相对上一版本的变化：

   > "**修改 v1 → v2：** 在 VAR 中加入名义有效汇率。滞后阶数不变（4）。Cholesky 顺序更新：
   > 汇率排在政策利率之后。
   >
   > **对结果的影响：** 价格之谜消失了：货币紧缩后价格下降。产出响应略小（峰值 -0.25%，
   > 之前为 -0.31%）。汇率在冲击当期升值，与非抛补利率平价（UIP）一致。"

### 哪些可以改

全部都可以：知识库（第 0a 阶段）、模型类别（第 1 阶段）、设定（变量、排序、滞后、识别、先验、
样本）、数据（来源、变换、频率、用户提供的 CSV）、估计设置（抽样次数、预烧期、收敛标准、
所用的库或语言）、合理性检查及其阈值（例如保留用户有理论依据的价格之谜），以及呈现的每个
部分（受众、风格、语言、叙述、组成部分、格式）。

### 并行设定

用户可能想同时跑多个设定并比较：

- "分别用 4 阶和 8 阶滞后跑一下，两个都给我看。"
- "用 Minnesota 先验和 Sims-Zha 先验各估计一次。"
- "把 BVAR 和 LP 的结果并排放。"

把每个设定作为研究日志里的一个并行分支保存（结构见
[`research-log/SKILL.md`](../research-log/SKILL.md)）。`VARReport` 可以加入基准与备选的
对比图。

### 修改 skill 本身

SKILL.md 文件和根目录的 `config.yaml` 都是纯文本。用户可以自己改，也可以让 agent 改，例如：
"把 `config.yaml` 里默认的总体先验紧度（lambda_1）改成 0.2。"修改从下一次调用起生效。
往 `scripts/lib/` 里加方法属于开发工作（见
[DEVELOPMENT.md](../../DEVELOPMENT.md#how-to-add-a-new-estimation-method)）。研究日志会为
每次分析记录脚本路径和内容哈希。

### 平稳处理流程中途的修改

用户打断流程提出修改时：

1. **立即回应修改。** 不要坚持先把当前阶段做完。
2. **保存当前进度。** 已经算出来的结果全部保留。
3. **找出最少的返工。** 只重跑受修改影响的部分。
4. **确认计划。** 告诉用户："你改了 X。这意味着我需要重跑 Y 和 Z 阶段，A 和 B 阶段不受影响。
   可以继续吗？"
5. **执行并展示差异。** 说明结果有哪些变化。

## 工作流各阶段

### 运行完成契约

当用户暂停、转向其他话题，或上下文被压缩时，一次运行可能在第 6–7 阶段（报告、处置）之前
就沉寂了。三个机制让每次运行在第 7 阶段关闭之前始终处于可见的"未完成"状态：

1. **持久的运行状态。** 从第 1 阶段起，在运行的研究日志旁维护 `run_state.json`。它的结构和
   生命周期由 research-log skill 规定
   （[`research-log/SKILL.md`](../research-log/SKILL.md#run-state-file-run_statejson)）。
   每过一个阶段关口就更新它，与该阶段的日志条目同步写入。它是上下文压缩后仍然存在的锚点：
   任何恢复的或被压缩过的会话，行动之前先读它。

2. **借助环境的任务跟踪。** 在第 1 阶段（模式确认之后），如果 agent 环境提供任务跟踪工具，
   为剩下的每个阶段建一个任务（"第 2 阶段：设定"……"第 7 阶段：处置"），并在运行通过各个关口时
   把它们更新为进行中 / 已完成。这样，待办阶段对 agent 和用户都可见，不依赖对话文本。没有任务
   工具时，只靠 `run_state.json` 记录状态。

3. **完成的定义。** 一个阶段只有在其产出存在、*并且*研究日志条目已追加之后才算完成。报告是
   工作的一部分，不是尾声：

   | 阶段 | 完成的标准 |
   |---|---|
   | 1–3 | 用户确认了决策 + 已追加日志条目 |
   | 4 | 产出写入同目录的 `outputs/` + 已运行诊断 + 日志条目 |
   | 5 | 已给出合理性结论（通过 / 指出的异常）+ 日志条目 |
   | 6 | 已交付 `report.html` 和文字解读 + 日志条目 |
   | 7 | 已记录处置和工具审查；`run_state.json` 已关闭 |

**在结束任何一段工作的回复之前**（交付了结果、回答了问题、解决了错误）：检查运行状态。
如果有一次运行处于 `open` 且停在第 7 阶段之前，要么推进到下一阶段，要么明确说明还剩什么并
建议何时完成。明确的、有记录的推迟可以接受；沉默不行。

### 第 0a 阶段：知识库初始化（一次性）

做任何分析之前，先检查当前背景是否已有知识库。

1. 如果 `skills/knowledge-base/context/` 里有内容，加载它，并向用户概述关键参数以便确认。
2. 如果是空的（首次使用），请用户描述其经济体和制度背景。生成草稿模板请用户审阅。这只发生一次。
   **快速通道：** 如果请求是标准的美国分析 / 使用预置面板的分析（经典复现，或字典已覆盖美国
   情形的模式 C 问题），建议*跳过*访谈（"这次运行不需要本地知识库；字典提供了美国背景"），
   用户同意后直接继续。不要在不需要背景的运行里强制做入门访谈。**非美国的一次性分析：**同样
   适用快速通道：建议以字典条目为锚、辅以模型自身的本地知识继续，并在每处来源说明中*明确标注为
   模型自身知识*；只有当用户预期会在这个经济体上反复工作时，才提出建立经济体概况。
   **中国：**如果用户预期会反复研究中国经济，建议建立中国的经济体概况（可参考
   `data/nbs_m/UPDATE.md` 中关于国家统计局数据口径的说明）。
3. 如果用户提供了论文或参考资料，通过 knowledge-base skill 把它们整理进知识库。

之后所有阶段都先查知识库，再退回到模型自身知识。研究日志记录每个决策依据的是哪个知识来源。

### 第 0b 阶段：受理与分流（每个请求）

按上面[三种入口模式](#三种入口模式)一节，把每个请求归入模式 A、B 或 C。分流是一段话的推理：

1. **扫描请求**，寻找模式表中的信号。
2. **在继续之前向用户说明模式**：*"这看起来是模式 A：你点名了 CEE (1999)，它在字典里。"*
3. **信号混杂或含义不清时，问。** 不要默默选一个模式。

**在研究日志中记录分流决定**，包括推理过程和匹配到的字典条目（如有）。如果会话中途换了模式
（见[模式转换](#模式转换)），也要记录。

### 第 1 阶段：各模式的入口流程

这一阶段的工作取决于第 0b 阶段确定的模式。每条路径都为下游阶段产出同样的东西：一个已确认的设定。

#### 第 1A 阶段：字典执行

字典条目已经写明了模型类别、变量、识别和样本。主控在这里要做的是：

1. 从 [`skills/model-dictionary/entries/<id>.yaml`](../model-dictionary/entries/) 读取条目。
2. 如果 [`scripts/replications/<id>/`](../../scripts/replications/) 已经存在，向用户概述其
   `config.yaml` 和 `README.md`。确认用户想要的设定改动（不同的样本、不同的数据替代）。
3. 如果复现目录不存在，勾勒出等价方案：会调用哪些 [`scripts/lib/`](../../scripts/lib/)
   函数（例如 `fit_var` → `cholesky_irf` → `VARReport`），需要哪些数据，FRED-MD/QD 面板
   能提供哪些替代。

在进入数据收集之前，**等用户确认**设定和任何偏离。只有用户要求偏离时才转到第 2 阶段；
否则直接跳到第 3 阶段。

#### 第 1B 阶段：论文提交

估计之前，主控必须把论文转成一个经过核验的字典条目。

0. **先查重。** 识别论文（打开文件，至少读到标题页；绝不相信文件名），在字典中搜索：引用信息、
   `verified.pdf_location` 和 id。如果已有经过核验的条目，这是**模式 A，不是 B**：告诉用户，
   转去模式 A，不要起草重复条目。
1. **核实暂存的文件**，然后提取论文的设定。先查完整性：文件能打开，页数合理，标题页与用户给的
   引用一致。解析之前先报告你的发现。PDF 用 `pdf` skill，URL 用网页抓取，或者直接用用户提供
   的文本。**纯图像扫描件**（没有文字层，2000 年以前的 JSTOR PDF 很常见）：用环境里可用的
   PDF 渲染工具把页面渲染成 PNG（正文约 150 dpi；设定所依赖的表格、脚注和数据附录用约 300 dpi
   重新渲染），然后读图；引用页码时注意扫描页码与期刊页码的偏移；读不准的数值要指出来，不要猜，
   并向用户提供重新做 OCR 后暂存的替代方案。
2. 委托 `model-dictionary` skill 按其[结构](../model-dictionary/SKILL.md#entry-schema)起草
   条目。保存为 [`entries/<id>.yaml`](../model-dictionary/entries/)，并附上
   `AUTO-GENERATED: please verify` 注释。核验状态（`draft | checked_against_paper |
   signed_off`）：如果条目是**依据暂存的 PDF 逐字段起草、每个定义设定的字段都有页码**，
   那就是 `checked_against_paper`，因为起草和核对同时完成了。凭记忆、摘要或二手资料起草的
   条目，在对照论文核对之前都是 `draft`；见 [DEVELOPMENT.md](../../DEVELOPMENT.md)。
3. 把草稿给用户看。重点标出：识别方式的选择、样本起止、变量代理、先验超参数，以及论文隐含做出
   的任何判断。把含糊之处摆到明面上，不要掩盖。
4. 如果方法在 [`scripts/lib/`](../../scripts/lib/) 里没有实现，调用 `advisor-protocol`
   （如已启用）推导算法。把核验过的推导保存为参考文档，以后可以变成新的 `scripts/lib/` 函数。
5. 用户核验条目之后，以该条目为设定来源**转入第 1A 阶段**。

继续之前**等用户核验**条目草稿。

#### 第 1C 阶段：研究设计

委托 `model-selection` 子 skill。

1. 理解研究问题和分析目标。
2. 评估数据情况（变量个数、样本长度、频率）。
3. 通过 `model-dictionary` skill **在字典中搜索**匹配条目。如果有一个或多个强匹配，建议升级为
   使用该条目的模式 A，并明确告知模式转换。
4. 如果没有干净的匹配，依据模型自身知识推荐 1–3 个候选模型类别并说明理由。
5. 进入设定设计之前**等用户确认**。

对于以开放研究问题提出的 Sims (1980) 式请求（"货币政策如何影响产出？"），这一阶段会在字典里
找到 `sims_1980_var` 和 `cee_1999_monetary_svar`，并建议升级为模式 A。

通过 research-log skill **记录这一阶段**，包括模式和字典匹配（如有）。

### 第 2 阶段：设定

**各模式的适用情况。** 在模式 A 中，这一阶段主要是确认：字典条目已经决定了一切。在模式 B 中，
第 1B 阶段起草的字典条目是输入；设定决策变成"核验或推翻草稿"。大部分设定设计发生在模式 C。

委托 `specification` 子 skill，它负责框架的**标准决策层级**（只在那里定义一次；见
[`specification/SKILL.md`](../specification/SKILL.md#decision-hierarchy)）：

> **用户 ▸ 模型字典 ▸ 知识库 ▸ 模型自身知识 ▸ 数据驱动的搜索**，每一层都要检验**经济逻辑**。

第 2–4 层是*组合*使用，而不是严格的逐级退让。字典提供锚点，知识库把它调整到本地情形，
模型自身的推理填补空白；只有两个来源在同一字段上冲突时，这个顺序才用来裁决（模式 A 中，
为了忠实于原文，字典锚点占主导；模式 C 中，知识库把它调整到本地经济体）。数据驱动的搜索只限于
超参数 / 滞后阶数，从不用于变量选择或识别。

specification skill 决定：
- **变量选择：**理论优先，参考知识库和文献。绝不由数据驱动：变量进入模型，是因为经济学认为
  它们应该在里面。
- **滞后阶数：**信息准则搜索（AIC、BIC、HQ），可由经济逻辑推翻（例如残差自相关、合理的传导
  滞后）。
- **先验超参数：**采用文献默认值，可以用网格搜索细化，但网格搜索只筛掉不稳定和估计失败的情形。
  经济检查（冲击当期符号、价格之谜）是报告的诊断项：它们触发调查和第 3 类提案（见第 5 阶段），
  而不是自动否决。
- **识别：**纯理论选择，依据研究问题、知识库和文献。绝不按数据拟合来选。
- **样本区间：**依据对制度变化的认识（来自知识库），以及样本长度与结构同质性之间的权衡。

每个决策都附有理由和知识来源（用户、知识库、文献、模型自身知识或数据驱动），做到完全透明。

字典运行中，从条目里读取设定（例如 `entries/sims_1980_var.yaml`），而不是凭记忆，并概述变量、
样本、确定性项、识别和滞后。

把设定摘要交给用户，等确认后再继续。

通过 research-log skill **记录这一阶段**。

### 第 3 阶段：数据收集

委托 `data-retrieval` 子 skill：

1. 把每个变量对应到一个数据源（美国默认：FRED；中国默认：国家统计局面板 `nbs_m` / `nbs_q` /
   `nbs_a` 或 `nbs` fetcher，见 data-retrieval skill 的"国家统计局数据"一节）。
2. **如果这次取数会第一次把新数据写到磁盘上（新数据集、新来源，或手工粘贴的 CSV），取数之前先
   确定数据放在哪里**，按照 data-retrieval 的[运行时收集流程](../data-retrieval/SKILL.md#runtime-collection-workflow)
   和[数据获取处置](../data-retrieval/SKILL.md#data-acquisition-disposition)
   （草稿 / 缓存 / 预置 / 提交 / 丢弃）。如果本次运行已经商定了存储方式，或者数据集已经注册，
   就跳过这一步。
3. 用程序获取序列。
4. 给出汇总表：变量名、来源序列 ID、频率、样本覆盖、单位、季节调整状态。
5. 提出变换建议（取对数水平、一阶差分、季节调整），并说明经济理由。
6. **等用户确认**变量对应关系和变换。
7. 确定 fetcher 代码的去向（临时 / connector / lib fetcher），以及是否把缓存提升为预置数据集。
   这是第 7 阶段代码处置在数据层的对应环节；这些决定都要记录。

经典复现的变量对应关系写在其 `config.yaml` 里（例如
`scripts/replications/sims_1980_var/config.yaml`）。有些原始序列在 FRED 里没有完全对应的
序列：找出最接近的替代，解释差异，让用户决定。

**记录这一阶段**，第 2 步和第 7 步触发时，要同时记录两项数据获取处置选择（数据层级和
fetcher 层级）。

### 第 4 阶段：估计

估计通过 [`scripts/lib/`](../../scripts/lib/README.md) 完成。这个 Python 库封装了
`statsmodels`、`scipy`、`numpy` 和 `plotly`，并补上了这些包没有干净提供的宏观计量部件。
它的 README 是模块清单的权威来源。

没有按方法划分的 skill：每个方法的概念说明在其 `scripts/lib/` 模块的 docstring 里（固定下来的
数学约定在 CONVENTIONS.md）。主控生成一个薄脚本：读配置、调用库函数、保存产出。

1. **生成一个 `replicate.py` 风格的薄脚本**（约 150 行），遵循
   [`scripts/replications/` 的约定](../../scripts/replications/README.md)。脚本从自己目录下的
   `config.yaml`（不是根目录的那个）读取设置，用 `lib.load_dataset` 读数据，用 `lib.transform`
   做逐列变换，调用 `scripts/lib/` 的估计函数，把产出写到脚本**同目录**的 `outputs/` 子目录
   （`scripts/<tier>/<id>/outputs/`，不纳入版本管理；所有自带的复现都这样做，工作区根目录的
   `outputs/` 只是草稿区）。默认工作位置：
   - **模式 A**：使用现有脚本
     [`scripts/replications/<id>/replicate.py`](../../scripts/replications/)（经典）或
     [`scripts/applications/<id>/replicate.py`](../../scripts/applications/)（应用）。除非用户
     要求偏离，否则不需要新脚本。
   - **有用户偏离的模式 A**（不同的样本、变量、经济体）：变体不再是经典复现，所以在
     `scripts/applications/<描述性_id>/` 新建目录，不要动经典复现（规则与下面的模式 B/C 相同；
     见来源层级表和 `scripts/applications/README.md`）。
   - **模式 B 和 C**：把新脚本写到 `scripts/applications/<id>/replicate.py` 作为工作位置。
     **最终层级**（留在应用、提升为经典，或丢弃）在第 7 阶段（处置与归档）决定。
2. 用确认过的设定估计模型。
3. 报告该方法产出的结果。VAR 类模型包括系数摘要、后验分布（如为贝叶斯）、滞后阶数准则（AIC、
   BIC、HQ）和稳定性（伴随矩阵的特征值）；其他方法报告各自的产出（例如滤波后的序列、因子载荷）。
4. 在方法支持的情况下运行 `diagnostics` 子 skill；否则说明哪些检验不适用。

**暂时不要展示脉冲响应。**先确认模型设定良好。

**记录这一阶段**，包括调用的确切 lib 函数及其关键参数（抽样次数、滞后阶数、识别方案），
使得仅凭日志就能复现这次运行。

### 第 5 阶段：经济合理性检查

这是关键关口。**与第 4 阶段的分工：**`diagnostics` 子 skill（第 4 阶段）负责*统计*充分性
（残差自相关、ARCH、正态性、伴随矩阵稳定性）。第 5 阶段*使用*这些诊断（不重新计算），并在此
基础上加上下面的*经济*判断。评估：

1. **稳定性。**报告最大根，把动态归类为平稳（小于 1）、单位根（在抽样误差范围内等于 1）或爆炸
   （大于 1）。一致地应用所声明的模型类别和复现标准，把近单位根的抽样不确定性作为公开披露的
   诊断项，不要凭有限期的图形认定稳定。
2. **残差诊断。**没有严重的自相关，异方差大体可接受，正态性是软要求。
3. **关键响应的符号和量级。**以货币政策冲击为例（Sims）：
   - 产出是否下降？（预期如此）
   - 价格水平最终是否下降？（如果没有，指出"价格之谜"）
   - 失业率响应的量级是否符合奥肯定律？
   - **收敛性，取决于冲击类型。***暂时性*冲击的响应应在合理的期限内（24–40 个季度）消失。
     *永久性*冲击的响应（长期约束识别的冲击，如 Blanchard-Quah 供给冲击，或单位根系统中的水平
     响应）必须**收敛到一个有限的极限**，而不是消失；在这些情形下要求响应消失，会按构造否定
     正确的模型（框架自带的 BQ 复现就是典型例子）。
4. **预测误差方差分解。**各部分份额在经济上是否合理？

检查不通过时，先诊断原因，再按类别处理：

1. **实现或数据错误**（变换错误、样本没对齐、序列标签错误、编码疏漏）：修正后**自动回到
   第 4 阶段**。这些是纠错，不是设定搜索。
2. **事先规定的统计规则**（按文档里的默认办法恢复稳定性、按说明的准则选滞后阶数）：应用规则并
   自动重跑，记录所用的规则。第 1、2 类共享 **5 次自动迭代**的额度；用完之后，展示所有尝试，
   请用户指示。
3. **出于经济考虑的实质性改动**（变量集合、排序、样本区间、先验设置：任何会把结果推向预期符号
   的改动）：**绝不自动进行**。说明哪项检查没通过、为什么在经济上重要，把补救办法作为待确认的
   选项提出（按 diagnostics skill 的"提案 → 确认"规程），并把被接受的备选设定作为带标签的
   稳健性分析，与基准**并列**运行。第一遍的结果保留并报告，绝不悄悄替换。
4. **出乎意料但干净的结果**（符号与先验相反，但没找到错误）：报告并解释；这可能正是研究发现，
   而不是缺陷。绝不按结果选择设定（见 CLAUDE.md 的"先停下来问"清单）。

检查通过时：
- 给出结果及其解释。
- 定稿之前**等用户确认**。

#### 设定搜索：这道关口的代价与披露规则

*朝着预期符号的方向*反复修改设定直到检查通过，按构造就是**设定搜索**（预检验 / 分岔路径
花园）：最终结果无法证伪检查中隐含的先验，经过这样的搜索之后，常规的置信区间或可信区间也不再
具有名义覆盖率。这道关口仍然值得保留（悄悄交出一个价格之谜更糟），但它的代价必须可见，而不是
只记在日志里。因此：

1. **始终在最终报告中披露搜索过程。**第 6 阶段的文字解读必须说明由合理性检查引发的修改次数
   （包括零次："第一个设定就通过了"），并概述每一步改了什么（以研究日志的版本历史为依据）。
2. 只要发生过由合理性检查引发的修改，就**把第一遍结果和最终结果并列展示**，通常是关键冲击的
   基准脉冲响应图，让读者看到搜索改变了什么。
3. **说明区间是以搜索为条件的。**在文字解读中写一句：报告的区间没有考虑之前的设定修改。
4. 现有的硬性规则仍然有效：绝不为迎合故事重新给冲击贴标签，绝不为通过检查而放宽阈值（见
   specification skill）；"接受异常"这条路（*有理论依据地*保留价格之谜）始终可选，而且往往是
   更恰当的处置。

**记录这一阶段，包括失败的迭代及其理由。**

### 第 6 阶段：结果与报告

委托 `results-presentation` 子 skill：

1. **生成交互式 HTML 报告**作为主要产出，使用 `scripts/lib/report.py`（`VARReport` 类），
   保存为运行同目录 `outputs/`（`scripts/<tier>/<id>/outputs/`）里的 `report.html`。
   按 results-presentation 中与方法相适应的章节规则选择章节。每份报告都包含设定摘要、文字解读
   和研究日志。不可用或不适用的诊断、结构量和推断要明确标出；不要用编造的章节填位置。
2. **PDF 图和 LaTeX 表格是可选的，按需提供**，用于投稿或印刷。自带的复现只产出 HTML 报告 +
   JSON 结果；不要把 PDF/LaTeX 当作默认交付物。
3. 确定目标受众（期刊、工作论文、政策简报、演示、内部），与 `results-presentation` 的受众
   枚举对应。
4. 查知识库中的内部风格和格式惯例。
5. 按受众撰写文字解读。
6. 做沟通合理性检查：文字解读是否准确反映了结果中的不确定性？
7. 把会话日志（`session_research_log.json`）及其 Markdown 摘要（`research_log.md`）保存到
   输出目录（见 research-log skill）。

估计脚本（第 4 阶段默认保存在 `scripts/applications/<id>/`）应以生成 HTML 报告作为最后一节。
所有产出都写到脚本同目录的 `outputs/` 子目录（`scripts/<tier>/<id>/outputs/`），它被
gitignore：脚本纳入版本管理，生成的模型产出可以重新生成。写在那里的会话记录
（`session_research_log.json`、`research_log.md`、`run_state.json`、任何保存的计划）不能
重新生成，删除 `outputs/` 之前必须复制出来。（工作区根目录的 `outputs/` 是尚未归入层级的临时
运行的草稿区。）

把一切交给用户做最终审阅，然后进入第 7 阶段确认处置。

### 第 7 阶段：处置与归档

第 6 阶段产出结果和报告之后，**明确询问用户如何处理刚生成的代码**。这是治理环节，防止工作
文件不断累积却没有最终归宿。

这一阶段**在每次会话结束时都是必需的**，失败的运行也不例外。绝不让处置停留在隐含状态。
`outputs/`、工作脚本和半成品应用就是这样越堆越多，最后分不清哪些是真正的研究、哪些是试验。

**可观察的触发信号。**"会话结束"是观察不到的，因为没有用户会宣布它。一旦出现下面任何一个具体
信号，就提出处置建议，而不是等待一个永远不会被宣布的结束：

| 信号 | 行为 |
|---|---|
| 用户接受第 6 阶段的结果（"谢谢""看起来不错""这就是我要的"），没有修改要求 | 现在提出处置建议 |
| 运行尚未结束时，用户转向无关话题 | 指出这次未完成的运行，在新话题之前（或同时）提出处置建议；转换话题不能让运行悄悄成为孤儿 |
| 用户问收尾性质的问题（文件在哪、怎么引用、"还有别的吗？"） | 把处置建议放进回答里 |
| 运行陷入无法解决的停滞（合理性循环用完、数据不可得、用户对某个关口没有回应） | 失败的运行也要处置，通常是**丢弃**或**继续迭代**，并附 `next_steps` 说明 |

如果用户仍在流程中（又要求一次修改），处置可以等，但运行在 `run_state.json` 中保持 `open`，
[运行完成契约](#运行完成契约)会让待办阶段一直可见，直到第 7 阶段关闭它们。

#### 五个选项

1. **仅归档。**把产出留在运行同目录的 `scripts/<tier>/<id>/outputs/`。不提升脚本。适用于成功
   但一次性的、以后可能回看的分析。下次会话能看到产出，但没有提交的脚本；回来时再决定。

2. **保存为应用**（检查通过的模式 B、C 的默认选项）。把这次运行保留 / 提升到
   [`scripts/applications/<id>/`](../../scripts/applications/)，包括：
   - `README.md`：论文 / 问题、做了什么、主要发现、注意事项
   - `config.yaml`：完整的设定选择（如有字典条目，与之对应）
   - `replicate.py`：可运行的脚本
   脚本的 `outputs/` 仍然 gitignore。如果有字典条目，从条目链接到这个应用，并保持其
   `verified.status` 不变：批准一个应用并不等于对照论文核对过条目。在会话日志中记录批准。新条目
   从 `draft` 开始；何时升级由 model-dictionary skill 规定。

3. **提升为经典。**移到 [`scripts/replications/<id>/`](../../scripts/replications/)，并创建或
   更新对应的字典条目（`verified.status: checked_against_paper` 或更高）。仅限忠实于原文、经过
   严格核验的公共示例，通常是明确复现了一篇已发表论文、结果在合理容差内一致的工作。**少见。**

4. **继续迭代。**一切留在当前工作位置。适用于跨多次会话的活跃开发。在研究日志中记一条
   `next_steps`，让下次会话知道从哪里接着做。

5. **丢弃。**适用于失败的运行（合理性检查无法解决）、与经典工作完全重复的运行，或死胡同。
   先把会话记录（`session_research_log.json`、`research_log.md`、`run_state.json`、任何保存的
   计划）从 `scripts/<tier>/<id>/outputs/` 复制出来，因为它们不能重新生成。然后删除那个
   `outputs/` 目录和任何未保存的工作脚本。对于**模式 A 的经典运行**，什么都不删（其生成的产出
   可以重新生成，留在原处即可），只在日志中记录处置。对于只有计划的会话（例如推迟的取数），删除
   任何脚手架之前，先在日志中引用或指向那份计划。

#### 决策参考

根据会话的模式和结果提出具体选项：

| 会话信号 | 建议的处置 |
|---|---|
| 模式 A 经典运行；结果符合预期 | **仅归档**（经典复现已经存在） |
| 模式 B 论文提交运行；合理性检查通过 | **保存为应用** |
| 模式 C 研究设计运行；合理性检查通过；新设定 | **保存为应用** |
| 模式 C 运行，结果与某篇已发表论文高度一致 | **提升为经典**（少见） |
| 任何模式；合理性检查无法解决 | **丢弃**或**继续迭代** |
| 任何模式；用户说明这次是框架测试 | **丢弃** |

提出建议时总是附上理由，例如：

> *"合理性检查通过；这是一次模式 C 运行，用的是新的大宗商品价格设定。我建议**保存为应用**，
> 放在 `scripts/applications/eu_commodity_spillover/`。其他选项：仅归档 / 提升为经典 /
> 继续迭代 / 丢弃。选哪个？"*

用户确认或另选。按设计原则 3，绝不空白地问"这个你想怎么处理？"；总是带着理由提出建议。

#### 记录

处置记录在研究日志中：

```yaml
disposition:
  decision: "save_as_application"   # archive | save_as_application | promote_canonical | continue | discard
  decided_at: "2026-05-19T17:42:00Z"
  destination: "scripts/applications/eu_commodity_spillover/"
  rationale: "模式 C 新设定；合理性检查通过；可复用于欧盟溢出研究"
  dictionary_entry_updated: false
  prior_runs: []                    # 同一 <id> 下被取代的旧运行
```

**记录这一阶段。**即使是"仅归档"和"丢弃"也要记录，因为以后的会话需要知道过去的工作去了哪里、
为什么。

#### 工具审查（子步骤）

代码处置针对的是脚本。会话里还会写一些内联辅助函数，其中一些可以复用。审查它们，免得以后的
会话重写或手工复制同样的逻辑。

代码处置决定记录之后，**自动列出**本次会话脚本里写的辅助函数，并为每个函数提出处置建议。
**默认是"保持临时"**；提升到 lib 应由用户明确选择。

##### 哪些函数算数

包括会话的 `replicate.py` / `scripts/applications/<id>/*.py` 中定义的、满足以下条件的函数：

- 至少约 5 行实质代码（跳过简单的 lambda / 一行函数）。
- 至少有一个类型明确的参数（不是 `def main():` 这类入口函数）。
- 不是从 `lib` 或其他框架模块导入的。

跳过：

- 对某个 lib 函数的一行封装。
- 函数体实际上只是一次库调用。
- 专门服务于本脚本控制流的闭包 / 装饰器。

##### 每个函数的三个选项

1. **保持临时。**函数留在原处，不再处理。如果函数签名引用了复现特有的名字（例如论文里写死的
   变量名），或逻辑与这篇论文的数据结构紧密耦合，默认选这个。

2. **标记待提升**（"候补队列"）。把函数名、签名、位置和建议的 lib 归属追加到
   `skills/research-log/tools_to_promote.yaml`（结构和合并规则见
   [`research-log/SKILL.md`](../research-log/SKILL.md#tool-promotion-queue)）。lib 暂不改动。
   标记跨会话保留；以后的会话写出类似函数时，agent 会指出之前的候选并建议合并。适用于看起来通用、
   但还没出现第二个调用者的函数。

3. **现在提升到 lib。**把函数加到合适的现有 `scripts/lib/` 模块（没有合适归属时新建一个；
   不适合单一方法模块的工具可以放到兜底的 `lib/utils.py`）。要求：至少有一个冒烟测试，符合框架
   的 docstring 约定，并检查没有破坏模块依赖关系（DAG）。仅限在*本次*会话中用了不止一次的函数，
   或用户明确要求立即提升。拿不准时退回选项 2，因为提升会立即带来维护负担。

##### 决策信号

对每个候选函数，向用户列出：

| 信号 | 建议 |
|---|---|
| 本次会话中调用了不止一次 | 现在提升 |
| 函数签名引用了复现特有的名字 | 保持临时 |
| 与之前会话排队的候选相匹配 | 提升（合并） |
| 通用但第一次出现 | 标记待提升 |
| 少于 10 行且只是简单封装 | 保持临时（低于门槛） |
| 显然属于某个现有 lib 模块（如 dating、irf） | 标记，并填写 `proposed_lib_home` |
| 会话处置为**丢弃** | 保持临时；不要把即将删除的脚本里的函数排进队列；在研究日志中记下观察，如果模式再次出现再标记 |

为每个候选提出具体决定并说明理由，例如：
*"`cumulative_multiplier(beta_g, beta_gdp, h, y_g)`：12 行，本次会话用了两次（扩张期和
衰退期）。我建议现在提升到 `scripts/lib/lp.py`。"*

按设计原则 3，绝不未经确认就自动提升。即使建议"提升"，也要等用户同意后才改动 lib。

##### 补充的"先停下来问"条目

- 没有至少一个冒烟测试就把工具提升到 lib → **停，先写测试**
- 提升一个签名里带有复现特有名字的函数 → **停，先把接口通用化**
- 关闭运行时跳过工具审查子步骤 → **停，执行它**
- 未经用户确认就自动提升 → **停，默认是"保持临时"，不是"提升"**

### 何时调用顾问

在任何阶段，如果某个数学内容无法有把握地转成代码（例如用户提供的论文中有新的先验或识别方案），

情况下继续。把核验过的产出保存为参考文档，免得同一推导再次升级。

## 错误处理

- 数据获取失败（API 宕机、序列停更）时，告诉用户并建议替代方案。
- 估计不收敛时，报告诊断结果并建议修改先验 / 设定。
- 绝不悄悄吞掉错误。每个失败都要记录并告知用户。
