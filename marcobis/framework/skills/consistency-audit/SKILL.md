# 一致性审计

框架的三层（`skills/` 工作流 + 知识、`scripts/lib/` 实现、`skills/model-dictionary/` 设定）不能
悄悄地彼此脱节。

有**两道防线**，两道都要跑：

| 防线 | 位置 | 频率 | 能发现 |
|---|---|---|---|
| **机械检查** | `tests/test_doc_consistency.py` | 每次运行测试（自动） | YAML 解析错误、索引与条目不一致、过时的模块数 / 条目数、无效的 `verified.status`、skill 到文件的失效链接、悬空的 `lib.*` 引用、缺少核心文件的复现目录 |
| **语义检查** | 本 skill | 按需 | 阶段编号是否连贯、提案 / 确认的流程、文档与实际做法是否一致、孤立或重叠的 skill、术语漂移（正则表达式无法做的判断） |

机械检查是必要的，但**不够**：测试全绿而工作流不连贯，框架仍然是坏的。语义检查也要做。

**中文化后的注意事项：**`test_doc_consistency.py` 中检查"模块数 / 条目数"表述的正则只匹配英文
措辞，翻译成中文的文档不受这两项检查约束。语义审计时要人工核对中文文档里的数字（模块数、条目数、
复现数）。其余机械检查（链接、`lib.*` 引用、YAML、索引）不受影响。

## 何时运行

- 用户要求审计 / 检查框架，或"把端到端流程走一遍"。
- 把工作提升为经典之前，或发布之前。
- **对 skills、lib 或字典做了一批修改之后**，尤其是重建了某篇论文的复现。重建可能悄悄破坏依赖它的
  测试和文档。

## 步骤

### 第 1 步：机械检查（快速、确定）

```
python -m pytest tests/test_doc_consistency.py -q
```

每个失败都是一处具体的漂移，并带有 `file:line`。逐个修复或报告。如果审计中发现了一类新的、*可以
机械检查*的漂移（数量、引用、解析、路径），**把它编成一个新测试放在这里**，使它永远不会回归。机械
防线就是这样增长的。

### 第 2 步：语义审计（判断）

正则表达式读不懂含义。通过阅读各 skill，检查：

1. **阶段编号是否连贯。**以主控为准：第 0a 阶段（知识库初始化）和第 0b 阶段（受理与分流）并入第
   1 阶段的日志记录；第 1 阶段 = 各模式的入口流程，2 = 设定，3 = 数据，4 = 估计，5 = 合理性，
   6 = 结果，7 = 处置。每个提到阶段的子 skill 都必须与之一致。
2. **提案 → 确认的流程。**每个涉及决策点的 skill 都必须*提出具体选择并说明理由，然后等待确认*，
   绝不空白提问（设计原则 3）。指出只做描述的 skill。
3. **文档与实际做法。**抽查 skill / CLAUDE.md 的说法与代码实际行为是否一致：输出路径、默认
   超参数、文件位置、方法是否可用。中国数据部分还要核对 nbs-data skill、`data/nbs_*/UPDATE.md`
   与 `panel.yaml`、`nbs_update.py` 的行为是否一致。
4. **孤立 / 重叠的 skill。**主控调用表中的每个 skill 是否都能从某个阶段到达（或明确标为可选 /
   按需）？是否有两个 skill 做同样的检查却没有说明分工？
5. **术语 / 词汇。**同一个概念在各 skill 中用同一个名字，例如 `verified.status` 的三个级别
   （`draft | checked_against_paper | signed_off`）、模式标签（A/B/C）。
6. **来源优先顺序一致。**每处对知识来源优先链的表述都使用唯一的标准顺序：
   `用户 > 模型字典 > 知识库 > 模型自身知识 > 数据驱动`，每一层都检验经济逻辑；这一顺序只在
   `specification/SKILL.md` 中定义一次。

### 第 3 步：实际运行冒烟测试（证明路径能走通，而不只是文字通顺）

端到端运行一个较快的、已核验的复现，确认它仍然通过论文目标：

```
python scripts/replications/blanchard_quah_1989/replicate.py
```

预期看到 `6/6` 的论文目标对照表，以及脚本同目录 `outputs/` 下的输出文件。机械检查和语义检查都
干净、执行路径却坏了，框架仍然是坏的。（这个复现需要 FRED-QD 数据；没有时换一个已有数据的复现。）

### 第 4 步：报告与修复（提案，确认）

整理一份按优先级排列的问题清单（**P1** 会误导 agent 或用户 · **P2** 真实的摩擦或潜在的矛盾 ·
**P3** 润色），每一项附 `file:line` 和一行修复建议。按设计原则 3，**提出修复方案，等用户确认**后
再编辑；然后重跑第 1–3 步直到全部通过。在你自己的笔记里记录这次审计（日期、发现、处置）；如果某个
发现改变了行为，更新 CONVENTIONS.md 或 docstring。

## 添加新的不变式

审计发现一类新的漂移时，决定它属于哪里：

- **可以机械检查**（数量、引用、可解析性、路径、结构）→ 在 `tests/test_doc_consistency.py` 中加
  一个测试。**优先这样做**：它持续运行，不会被遗忘。
- **只能靠判断**（语义、流程、设计连贯性）→ 在上面第 2 步加一条，让下一次按需审计覆盖它。
